## Поток игры и сохранения

`GamePhase` в `lib/data/models/game_state.dart` содержит `morning`, `planning`, `dayAction`, `eventResolution`, `eveningSummary`, `finalSummary`. **Фаза `planning` сейчас нигде не присваивается**: при старте дня состояние `morning`, а подтверждение плана или пропуск переводит сразу в `dayAction`. Затем при необходимости идёт `eventResolution`, вечерний итог и следующий день; на 10-м дне — `finalSummary`. В `dayAction` ребёнок может работать, решать задания, покупать, распоряжаться копилкой. Демо-профиль позволяет переходить по дням и добавлять монеты, но хранится отдельно от обычной игры.

`GameRepository` (`lib/data/repositories/game_repository.dart`) сохраняет JSON `GameState` в `SharedPreferences`: ключи `finny_game_state_v1` (основная игра), `finny_demo_state_v1` (демо), `finny_demo_active_v1` (переключатель). Записи сериализуются через очередь `Future`, чтобы не перезаписывать новое состояние старым. Большинство вызовов движка вызывают `_save()` без ожидания результата; сбой записи обычно не показывается пользователю. Если JSON повреждён или не распознан, загрузка возвращает `GameState.initial()`, поэтому миграции и восстановление старых сохранений требуют отдельной проверки.

Внешность сохраняется **отдельно** от игры в `finny_appearance_v1` и `finny_demo_appearance_v1` (`lib/shared/widgets/finny_appearance.dart`). После переключения демо `DemoDrawer` вызывает `syncWithGameProfile()`. При сбросе прогресса проверять оба хранилища и то, что демо не меняет основную внешность. Поле `FinnyState.activeOutfit` есть в модели и JSON, но не участвует в выборе одежды на экране: это потенциальная точка интеграции купленных вещей.

## Экономика и правила, которые нельзя сломать

Значения ниже взяты из текущего кода. Основная петля настроена на 10 дней; первые 5 — обязательная демонстрационная история.

| Действие | Текущее правило |
| --- | --- |
| Начало | День 1: кошелёк **50 🪙**, копилка 0, запас еды на 1 день, цель по умолчанию «Ракета» (100). |
| Новое утро | Запас еды уменьшается на 1 день, если он был; затем доход дня поступает в кошелёк. День 2–5: по 10, день 6–7: по 20, день 8: 25, день 9: 20, день 10: 10. День 1 стартовые 50 уже зачислены. |
| План | `BudgetPlan.total = needs + wants + reserve + savings + leftover`; нельзя подтверждать отрицательные категории, сумму больше текущего кошелька и повторно подтверждать уже утверждённый план. План сам по себе не списывает деньги. |
| Работа у соседа | `completeWork()` добавляет **10 🪙** максимум один раз за день. Экран `work_screen.dart` содержит задания с ценниками и сбором заказа. |
| Учебное задание | Шесть задач в `financial_tasks.dart`, награда **5 🪙** за завершённую задачу только один раз по её стабильному ID. |
| Покупка | Списывает цену из кошелька; отрицательная цена, нехватка денег и повторная покупка постоянного предмета запрещены. Товар записывается в `PurchaseRecord`, еда добавляет дни запаса. Каталог сейчас содержит **10 предметов**. |
| Еда | Завтрак 7 🪙 на 1 день; набор 18 на 3 дня; большой набор 27 на 5 дней. На новом утре расходуется один день. В движке есть `triggerEmergencyAid()` (+1 день еды), но в текущем UI эта функция доступна только из демо-панели; автоматическая помощь в обычной игре **не подтверждена**. |
| Копилка | Взнос переводит положительную сумму из кошелька в копилку, не больше остатка до цели. Вывод возвращает сумму в кошелёк. Смена цели не уничтожает накопления. Получение полностью накопленной цели отдельно расходует нужную сумму из копилки и один раз записывает награду в инвентарь. Цели: скейт 60, домик 80, ракета 100. |
| Событие дня 5 | Ливень/крыша. Если ремонт требует сумму сверх кошелька, доступ к копилке разрешён только для предусмотренного выбора и при явном `useSavings`. Набор мастера может обнулить стоимость ремонта и расходуется один раз. |
| Конец дня | История фиксирует доход, траты, взнос, запас еды, настроение, план и фактические категории. Для **новых** записей `actualReserve` означает оставшиеся в кошельке деньги, `actualReserveSpent` — траты на запас/неожиданность, `reserveIsCash=true`. Старые записи могут хранить в `actualReserve` именно траты; не объединять их слепо. |
| Рост Финни | Этап `planner`: минимум 2 дня с едой, 2 дня с выполненным планом, 1 день с взносом. `independent`: 4/3/3 дня соответственно. Достигнутый этап не откатывается из-за одного трудного дня. |

`followedPlan` вычисляется в `lib/data/models/history_models.dart`. Для нового формата проверяются расходы по категориям, выделенный/непотраченный резерв, нужный взнос и еда; есть ветка совместимости для старых записей. При изменениях экономики смотреть одновременно `GameEngine`, `DaySummaryRecord`, экран вечернего итога и тесты `economy_test.dart`, `day_cycle_test.dart`, `learning_history_test.dart`.

## Персонаж и его внешний вид

Это **SVG/2.5D**, не 3D. `FinnySvg.render()` загружает локальный SVG, разбирает XML, скрывает/показывает группы по `data-accessory` и `data-part`, заменяет цвета по `palettes.json`, переключает глаза, рот, брови, куртку и шапки, добавляет нагрудный знак достигнутого этапа. `PetAvatarWidget` рисует результат через `flutter_svg`, слегка «дышит» и машет рукой по нажатию. Есть переключатель анимаций и уважение к системному `disableAnimations`.

Сейчас доступны ровно **3 пресета окраса** (`original`, `lagoon`, `apricot`), **3 цвета куртки плюс «без куртки»**, две шапки плюс «без шапки», очки и бант. Произвольного выбора цвета для тела и одежды пока нет. Заказанный ребёнком цветовой круг потребует дополнить модель хранения внешности и палитру SVG, сохранив читаемость глаз/лица и контраст элементов. Купленный `raincoat` находится в `inventory.ownedItemIds`; домашние виджеты передают `hasRaincoat` персонажу только при дожде. В `FinnySvg` дождевик сейчас принудительно заменяет куртку на синий вариант. В гардеробе нет действия «надеть купленный дождевик»; ребёнок справедливо воспринимает это как сломанную покупку.

Имя: `OnboardingScreen` передаёт введённое имя в `GameEngine.completeOnboarding()`, и `PlayerProfile.petName` сериализуется. При этом много реплик и семантическая метка аватара жёстко говорят «Финни»; домашний заголовок использует сохранённое имя. Жалобу «имя не устанавливается» нельзя закрывать одной проверкой JSON: пройти весь сценарий с новым именем, перезапуском приложения и экранными/речевыми текстами.

## Известные риски и незакрытые вопросы

1. **Детская понятность не подтверждена автоматическими тестами.** Игра остаётся текстозависимой; сценарии с ценниками, задания и статус на главном экране требуют переработки по результатам детского теста. Принимать исправления только после короткого прохождения ребёнком без подсказок взрослого.
2. **Имя/внешность/покупки расходятся между UI и моделью.** Имя в профиле есть, но реплики захардкожены; в каталоге уже есть emoji товара, однако `shop_modal.dart` рисует монохромные Material-иконки через `_itemIcon()`; приобретённый дождевик нельзя вручную надеть. Новые цветовые настройки должны мигрировать старые сохранения.
3. **Проверить запись прогресса после убийства процесса и перезапуска на телефоне.** Unit/widget-тесты покрывают сериализацию и демо, но текущая release-версия не прошла полный физический регрессионный обход после последней сборки.
4. **Релизная приёмка шире сборки.** Нужно ещё проверить требования исходного ТЗ на Android 8+/360 dp, доступность и крупные области касания, скорость первого запуска, работу офлайн, пользовательские настройки звука/анимаций, отсутствие потери прогресса, возрастную маркировку/страницу RuStore и права/лицензии на все материалы. Эти пункты не следует отмечать выполненными только по тестам Flutter.
5. **Нет истории Git.** Перед новым агентом сохранить точную копию `D:\Finny` или создать репозиторий с безопасным `.gitignore`; ключи подписи и локальные SDK/Gradle-данные исключены текущим `.gitignore`, но проверить это перед публикацией.
6. **Избегать массовых PowerShell-перезаписей исходников.** Ранее Windows Defender показал критическое предупреждение `Trojan:Win32/FileFix.BBA!MTB` на команду `pwsh.exe`, которая пакетно читала и переписывала несколько `.dart`-файлов. Это факт с пользовательского скриншота, не диагноз заражения или доказательство ложного срабатывания. Для изменений исходников предпочесть небольшие проверяемые патчи; при новом предупреждении не обходить защиту молча.
